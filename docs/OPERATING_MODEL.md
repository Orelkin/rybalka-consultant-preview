# Рыбалка — консультант · OPERATING_MODEL

## Роли постоянных рабочих чатов

### 00 MASTER — диспетчер
Состояние проекта, приоритеты, конфликты, handoff, итоговые решения.
Не выполняет длинную параллельную разработку или исследовательский архив.

### 10 APP — приложение / GitHub / PWA
Код, UI, deploy, QA, производительность, синхронизация.
Не создаёт заново рыболовную биологию, если claim уже есть в Knowledge Base.

### 20 KNOWLEDGE — база знаний
Наука, официальные данные, литература, виды, методы, claims/sources.
Не меняет UI приложения напрямую.

### 30 FIELD — мои рыбалки
Отчёты, фото, точки, уловы, снасти, успехи/нули.
Факт личной рыбалки не обобщается автоматически.

### 40 RECON — куда ехать
Региональная разведка, гидрология, доступ, правила, логистика, кандидаты.
Использует Knowledge Base, а не дублирует её.

## Work

START:
1. прочитать PROJECT_STATE;
2. проверить GitHub main HEAD;
3. выбрать одну активную задачу ROADMAP;
4. проверить, что другая сессия не делает тот же блок.

FINISH:
1. QA;
2. commit/артефакт;
3. запись в WORK_LOG;
4. обновление PROJECT_STATE при изменении статуса;
5. следующий блок только после фиксации.

## Фоновые исследования

### Literature lane
Только последовательный разбор архивов/журналов.
Не пишет UI.
Не запускает общую разработку.
Не дублирует научный поиск, если материал уже зарегистрирован.

### Research lane
Наука, официальная гидрология, правила, методы, регионы, свежие отчёты.
Не проходит журналы строго с №1 — это зона Literature lane.
Не пишет UI.
Результат: claims/hypotheses/regions/methods с источниками и confidence.

## Протокол от дублей

Перед новой работой:
- искать существующий claim/task;
- проверять WORK_LOG и GitHub;
- если задача уже ACTIVE — не начинать второй независимый вариант;
- если найден новый источник по существующему claim — усиливать/ослаблять его, а не создавать дубль;
- если изменение интерфейса не связано с активным ROADMAP — не внедрять его самовольно.

## Публикация

Пользовательская актуальная версия должна быть одна: GitHub Pages.
Старые публикационные поверхности — архив/диагностика до отдельного решения.

## Экономия токенов

Правило пользователя от 02.10.2026: выбирать минимальную достаточную глубину разбора в зависимости от задачи.

- Низкая: повторяющиеся операции по известному шаблону, оформление, копирование материалов, исполнение уже принятого решения.
- Средняя: обычные изменения приложения, локальная диагностика, проверка взаимодействия известных компонентов.
- Высокая: архитектура, перенос личных данных, неясные ошибки, противоречивые источники и достоверность сведений. После разрешения сложного вопроса снижать глубину для исполнения.

Использовать точечное чтение, сохранённые источники и готовые инструменты; объединять однотипные операции. Проверки выбирать по последствиям изменения и не повторять успешно пройденные без нового основания. Обязательные проверки фактов, личных данных и публикации сохраняются. Отчёты короткие; полный ZIP — после существенного этапа.

Если среда предоставляет инструмент выбора модели/уровня рассуждения, пользователь разрешает выбирать их автоматически под задачу. В текущем чате такого инструмента нет: правило применяется к глубине разбора, объёму контекста и операциям. Не выдавать это за фактическое переключение модели или настройки. Глобальные настройки и расписание этой инструкцией не меняются; отдельного разрешения на делегирование она не даёт.
